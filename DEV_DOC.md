# Developer documentation

This document is for anyone who wants to **set up, build, and work on** the
Inception codebase itself (add a service, change a configuration, debug a
container, etc.). For day-to-day usage of an already deployed stack, see
`USER_DOC.md`; for the general project overview, see `README.md`.

## 1. Setting up the environment from scratch

### Prerequisites

- A Linux virtual machine (the whole project must run inside one, see the
  subject).
- Docker Engine and the Docker Compose plugin (`docker compose`, not the
  legacy `docker-compose`).
- `make`, and `sudo` rights on the VM (the `host` target edits
  `/etc/hosts`).
- `openssl` available on the host (used by the `secrets` target to
  generate random passwords).

### Cloning and configuration files

```bash
git clone <repo-url> Inception
cd Inception
```

Two kinds of configuration are needed before the stack can start, and both
are already handled for you:

- **`srcs/.env`** is versioned in the repository. It only contains
  non-sensitive values (domain name, database name, WordPress usernames,
  site title, email addresses, `WORDPRESS_DB_HOST`). If you fork this
  project for your own login, edit `DOMAIN_NAME` here **and** `HOSTNAME` in
  the `Makefile` (see below) so both stay in sync.
- **`secrets/`** is git-ignored (only `secrets/.gitkeep` is versioned) and
  does not contain any file in a fresh checkout. Do not create these files
  by hand — run `make secrets` (or plain `make`, which includes it) to
  generate them:

  | File | Used for | Consumed by |
  |---|---|---|
  | `secrets/db_root_password.txt` | MariaDB `root` password | `mariadb` |
  | `secrets/user_db_password.txt` | Password of the WordPress DB user (`DB_USER`) | `mariadb`, `wordpress` |
  | `secrets/wp_admin_password.txt` | WordPress administrator password | `wordpress` |
  | `secrets/wordpress_user_password.txt` | WordPress author account password | `wordpress` |
  | `secrets/ftp_password.txt` | FTP account password | `vsftpd` |
  | `secrets/portainer_admin_password.txt` | Portainer administrator password | `portainer` |

  Each is a one-line random string (`openssl rand -base64 32` filtered to
  16 alphanumeric/symbol characters), generated by the `secrets` target in
  the `Makefile`. Every service reads its password(s) at runtime from
  `/run/secrets/<name>` (Docker's default secret mount point) — never from
  an environment variable — so no password ever appears in `docker
  inspect`, in an image layer, or in the Git history.

### Domain name

The subject requires the stack to be reachable at `<login>.42.fr`. The
`Makefile`'s `host` target takes care of this: it appends
`127.0.0.1 hdougoud.42.fr` to `/etc/hosts` on the VM (via `sudo`) if that
line isn't already present. `HOSTNAME` is declared at the top of the
`Makefile` — change it there (and `DOMAIN_NAME` in `srcs/.env`) if you
adapt the project to a different login.

## 2. Building and launching the project

Everything is driven by the root `Makefile`, which wraps `docker compose
-f srcs/docker-compose.yml`:

```bash
make          # = make host secrets up : first-time setup, then build + start
make build    # docker compose build      — (re)build every image
make up       # docker compose up -d      — start every service
make down     # docker compose down       — stop every service, keep data
make clean    # docker compose down --rmi all
make fclean   # docker compose down --rmi all --volumes --remove-orphans
make re       # fclean + build + up       — full rebuild, fresh containers
make host     # add hdougoud.42.fr to /etc/hosts (idempotent)
make secrets  # (re)generate every file under secrets/
```

`all` (the default target run by plain `make`) chains `host`, `secrets`,
then `up`. This is meant for the **very first** setup only.

> **Important**: `host` and `secrets` are declared `.PHONY` and `secrets`
> has no "already generated" guard, so both re-run their full recipe every
> time they are invoked — `secrets` will silently overwrite every password
> file with new random values on each run. Since WordPress and MariaDB
> only apply a password the first time they initialize their data (see
> their entrypoint scripts), running plain `make`/`make all` again after
> the stack has already been initialized will desynchronize the files in
> `secrets/` from the credentials actually configured inside the
> containers. In practice:
> - Use `make` only once, for the initial setup.
> - Use `make up` / `make down` / `make re` for every subsequent
>   start/stop/rebuild — none of them touch `secrets/` or `/etc/hosts`.
> - If you need to intentionally reset a password, see the "managing
>   credentials" note in `USER_DOC.md`.

To work on a single service instead of the whole stack:

```bash
docker compose -f srcs/docker-compose.yml build wordpress
docker compose -f srcs/docker-compose.yml up -d --no-deps wordpress
```

## 3. Managing containers and volumes

Useful `docker compose` commands (run from the repository root, always
with `-f srcs/docker-compose.yml`, or `cd srcs` first):

```bash
docker compose -f srcs/docker-compose.yml ps                 # status of every service
docker compose -f srcs/docker-compose.yml logs -f wordpress   # follow one service's logs
docker compose -f srcs/docker-compose.yml exec wordpress bash # shell inside a running container
docker compose -f srcs/docker-compose.yml restart nginx       # restart a single service
docker compose -f srcs/docker-compose.yml top                 # processes running in each container
```

Volumes and networks:

```bash
docker volume ls                     # list named volumes (mariadb, wordpress, portainer_data, ...)
docker volume inspect srcs_mariadb   # see mountpoint / metadata for one volume
docker network ls                    # list networks (ft-network among them)
docker network inspect srcs_ft-network
```

Since containers are declared `restart: unless-stopped`, killing a process
inside one (or a crash) makes Docker restart the container automatically —
you generally don't need to `up` it again manually.

Also useful when developing/debugging an entrypoint script: entrypoints
live under `srcs/requirements/<service>/tools/entrypoint.sh` and run every
time the container starts, but most of their setup logic (installing
WordPress, creating the database, creating the FTP system user) is
guarded by an "already initialized" check, so it only truly executes once
per volume's lifetime — delete the corresponding volume (see below) to
force it to run again.

## 4. Where project data is stored and how it persists

Two named volumes hold everything that must survive a container restart
or rebuild:

| Named volume | Mounted in container at | Contains |
|---|---|---|
| `mariadb` | `/var/lib/mysql` (in `mariadb`) | The WordPress database files |
| `wordpress` | `/var/www/wordpress` (in `wordpress` **and** `nginx`, read by NGINX to serve static/PHP files, and in `vsftpd` for FTP access) | The WordPress core, themes, plugins and uploads |

Per the subject's requirement, both are declared as Docker **named
volumes** (not bind mounts) in `srcs/docker-compose.yml`, with a local
`driver_opts` bind so Docker physically stores their data under
`/home/hdougoud/data` on the host — you can inspect the raw files there,
but you should always go through the named volume (not that path directly)
when configuring services, to keep the setup portable.

What this means in practice:

- `make down` / `make up` (or a host reboot) do **not** touch these
  volumes — the WordPress site and its database survive a normal
  stop/start cycle.
- `make clean` removes containers and images but still **keeps** the named
  volumes — safe to use when you only want to rebuild images from scratch.
- `make fclean` removes the named volumes as well — this wipes the
  WordPress database and website files entirely; the next `make up` will
  reinitialize both from empty, using whatever is currently in
  `secrets/`.
- `portainer_data` (a third named volume, without a host bind) similarly
  persists Portainer's own configuration/state across restarts.
